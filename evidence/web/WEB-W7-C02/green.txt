Post-review update: the reaping Job is now PROCESS-LIFETIME, not per-command.
core/sandbox/manager.py exports reaping_job_handle() — one reaping-only Job
per worker process (kill-on-close only, no limits), created lazily under a
threading.Lock, cached, never explicitly closed; the OS closes it when the
worker dies and reaps the tree. A per-command close killed intentionally
detached children (Start-Process/dev servers) — that regression is gone, and
the new test below proves both directions. Creation failure warns once and
caches the failure (documented choice); bind failure warns and runs anyway.
The os_sandbox-enabled path is unchanged: per-command sandbox Job, closed per
command, fail-closed.

== audit round 2 fixes ==

Finding 1 (P1, concurrent-init race in reaping_job_handle):
  core/sandbox/manager.py: _reaping_handle was published inside the lock at
  open_job() return (~old line 138), BEFORE assign_pid_to_job_handle +
  _reaping_self_assigned completed. A concurrent caller's lock-free fast path
  could observe (handle!=0, inherited==False) and take the per-command
  CREATE_SUSPENDED -> bind -> resume fallback — reopening the kill window
  self-assignment removed. Fix: open_job result goes to a LOCAL var inside
  _reaping_lock; worker self-assignment + _reaping_self_assigned complete
  first; _reaping_handle = handle is the LAST statement of init (double-
  checked re-read at lock entry unchanged). Fast-path readers now can only
  ever see a fully-initialized state; cached-failure semantics kept
  (creation failure -> _reaping_failed + warn once + 0; self-assign failure
  -> handle still published with inherited False = the documented fallback).
  Docstring now states the publish-last invariant.
  Probe (tests/web/w7/test_w7_c02_unit.py::
  test_w7_c02_reaping_handle_published_last): fake _windows() parks thread A
  inside assign_pid_to_job_handle; thread B calls reaping_job_handle() +
  reaping_is_inherited() concurrently.
    PRE-FIX : FAILED — B observed (3074, False): handle published while
              self-assignment still in flight (torn state reproduced).
    POST-FIX: PASSED — B blocked on _reaping_lock and observed only
              (3074, True); self-assignment confirmed True afterwards.

Finding 2 (P2, SSE cursor advanced on the id: line before data: consumed):
  Both SSE consumers counted an event on its `id:` line and broke mid-event,
  so Last-Event-ID resume skipped a payload that was never received
  (ids 1..5 "pass" while payloads are {1,2,4,5}). Fixed in
  tests/web/w7/test_w7_c02_module.py and
  platform_tests/web/chaos/run_recovery.py (scenario
  sse_disconnect_reconnect): new _sse_events() accumulates field lines and
  only commits a frame at the blank-line terminator; the reconnect cursor
  is the last COMPLETED event's id. Connection 1 still aborts mid-run over
  the real uvicorn socket — now deliberately consuming the next frame's
  `id:` line and dropping the socket before its `data:` arrives, proving a
  partially consumed event does not count as delivered. Assertions moved
  from id-line seqs to payload seqs parsed out of each complete event's
  `data:` JSON: the received-payload set must equal 1..final_seq exactly
  once across both connections.
  Probe: synthetic wire stream — old parsing counted ids [1,2,3], cursor=3,
  id-assertion "all 1..5" PASSES while payloads actually received were
  {1,2,4,5} (seq 3 silently lost); new parser keeps the cursor at the last
  complete event and the payload set comes out {1,2,3,4,5} exactly once.
    RESULT: old_defect_reproduced=True  new_correct=True
  Real-socket proof: pytest module test + chaos scenario below.

Finding 3 (P2, "?connect_timeout=3" appended unconditionally):
  run_recovery.py scenario_postgres_unreachable passed C02_URL =
  url + "?connect_timeout=3" to the PG-down worker; a URL already carrying
  query parameters became ...?a=b?connect_timeout=3 — psycopg reads the
  second '?' inside the previous value: silently no timeout. Fix: new
  _with_connect_timeout() parses with urllib.parse (urlsplit/parse_qsl/
  urlencode/urlunsplit), drops any existing connect_timeout key and appends
  connect_timeout=3 — '&'-merged when a query exists, '?'-merged otherwise.
    OLD: postgresql+psycopg://postgres@127.0.0.1:55432/rxycode?sslmode=disable?connect_timeout=3   (broken)
    NEW: postgresql+psycopg://postgres@127.0.0.1:55432/rxycode?sslmode=disable&connect_timeout=3
         make_url() parses query as {'sslmode': 'disable', 'connect_timeout': '3'}
  End-to-end: full chaos CLI re-run with
  --database-url .../rxycode?sslmode=disable — all 7 scenarios pass,
  postgres_unreachable still fails fast with OperationalError inside the
  pause (the & branch exercised live).
