# Composer 2.5 · 执行手册

> **这份文档不是计划，是纪律。** 它约束的是"主力模型怎么干活"，不是"要干什么活"。
> **模型分工权威**：[`MODEL-ASSIGNMENT.md`](./MODEL-ASSIGNMENT.md) —— **Composer 主写全部代码；Grok 只在写前端用到多模态（视觉）时才介入。**
>
> **适用范围**：本仓库与 LinkAgent 仓库的 **全部代码**：后端（Python / 协议 schema / appserver / 评测）+ 前端（Electron / React / TypeScript / 协议客户端 / UI）。
> **不写**：无。前端默认也是你的；卡里标注的「多模态环节」委托 Grok（见 C7）。
> **创建**：2026-07-31 · **修订**：2026-08-01（恢复主写定位：Composer 全栈，Grok 辅助前端多模态）

## §1 为什么需要这份文档

Composer 2.5 是一个**快**的主力模型。它的强项和弱项都很明确，施工文档必须围绕这两件事设计：

| 它很强的 | 它会翻车的 |
|---|---|
| 机械性的多文件改造（改类型、改签名、批量替换） | 长任务里保持目标不漂移 |
| 严格照着明确指令做 | 在没有明确指令的地方**自己发挥** |
| 快速迭代、快速试错 | 判断"这个任务算做完了吗" |
| 在给定文件里精确修改 | 记住十几个文件之间的隐含约束 |
| 按模板生成测试 | 权衡两个都说得通的设计方案 |

**推论：施工文档的每一张任务卡，都必须让它无需做任何设计决策就能完成。** 后端卡和前端卡都一样——前端视觉类决策除外，那部分交给 Grok（见 C7）。

凡是需要权衡的地方，文档里必须已经替它决定好，并写明"不要自己发挥"。凡是文档没写的，它必须**停下来问**，而不是猜。

## §2 八条硬规则

> 违反任何一条，这张卡的产出都要打回重做。

### C1 · 一次只做一张卡

**永远不要在一个会话里做两张任务卡。** 做完一张，commit，开新会话。

原因：Composer 2.5 在单个会话里做第二张卡时，会把第一张卡的上下文当成约束，产出会变形。这不是能力问题，是上下文污染。

### C2 · 不读整份文档，只读一张卡

施工文档动辄 40–100 KB。**不要通读。** 每张任务卡都是自包含的——背景、文件、命令、验收标准全在卡里。

正确姿势：
```
读 MODEL-ASSIGNMENT §0 → 读本手册 §2 → 读你要做的那张卡 → 开工
```

错误姿势：
```
读整份文档 → 上下文塞满 → 开始"综合考虑" → 产出漂移
```

### C3 · 用 Grep 锚点定位，不信行号

文档里的 `file:line` 是**写文档那一刻**的快照。你的第一次编辑落地之后，后面所有行号就全错了。

**每张卡都会给你 Grep 锚点**（一段唯一的代码文本）。用它定位：

```
✅  Grep "def _retrieval_text" → 找到真实位置 → 编辑
❌  直接跳到文档里写的 835 行 → 改错地方
```

行号只用来**判断这张卡的描述是否还新鲜**：如果 Grep 到的位置和文档写的差了 50 行以上，说明文档过期了，**停下来报告**（见 C8）。

### C4 · 只碰白名单里的文件

每张卡都有"涉及文件"表。**不在表里的文件一个都不许改。**

发现必须改表外文件时：**停下来报告**，不要顺手改。顺手改是 Composer 2.5 最常见的失败模式——它会为了让测试变绿而去改测试、改配置、改别的模块，最后 diff 里混进一堆没人 review 过的东西。

### C5 · 每张卡一个 commit，且必须能单独 revert

不要一个 commit 塞两张卡。不要把重构和功能混在一个 commit 里。

commit message 用卡里给的模板。**message 要说"为什么"，不是"改了什么"**——改了什么看 diff 就知道。

### C6 · 验收命令全绿才算做完

每张卡末尾都有一组**可直接复制粘贴**的验收命令。全部绿了才算做完。

- 命令报错 → 修，不要跳过
- 测试挂了 → 先判断是不是你的改动引起的（`git stash` 跑一遍基线对比），再决定修哪儿
- 命令跑不起来（环境问题）→ **停下来报告**，不要绕过去

**绝不允许**："测试挂了但我觉得跟我的改动无关，所以继续"。要么证明它在基线上也挂，要么修好。

### C7 · 前端也由你主写；多模态环节委托 Grok

**前端默认也是你的主写范围**：`frontend/`、`frontend/opentui-app/`、`frontend/protocol-client/`、`desktop/`（任何项目）、`*.tsx`、Electron `main`/`preload`——都在你的活里，不用请示。

前端卡里标注了「**多模态环节**」（视觉验收、图片类 UI、对照设计稿）的，**把那个环节委托给 Grok**——看截图、看设计稿是 Grok 4.5 选型的意义，也是你的视觉盲区。纪律在 [`GROK-FRONTEND-PLAYBOOK.md`](./GROK-FRONTEND-PLAYBOOK.md)，委托格式见 §4。

Grok 的产出由**你这张卡收口**：并入你的分支、跑全卡验收、统一 commit。你和 Grok 的唯一交接点是：卡里标注的多模态环节 + **`schema.json`（及协议契约测试）**——你产出并合并 schema 后，类型生成才开工。

### C8 · 卡住了就停下来问，不要发挥

以下任一情况出现，**立刻停止编码**，输出一段说明并等人回复：

| 情况 | 为什么必须停 |
|---|---|
| Grep 锚点找不到 | 文档过期或你找错仓库了 |
| 找到的代码和卡里的描述明显不符 | 同上 |
| 卡里的验收命令跑不起来 | 环境不对，继续做只会浪费 |
| 需要改白名单外的文件 | 范围外，需要人确认 |
| 前端卡里标了「多模态环节」但 Grok 不在 | 视觉环节是你的盲区，硬做会漏视觉 bug；等 Grok 或停下来报告 |
| 卡里没说清楚该选 A 还是 B | 设计决策不归你做 |
| 同一个错误修了 3 次还没好 | 你的假设错了，继续试只会越改越乱 |

**报告格式**：
```
STOP：<一句话说清卡在哪>
我做到了：<已完成的部分>
我需要：<具体需要什么决定或信息>
我没有改：<确认没有越界>
```

停下来问**不算失败**，猜错了继续往下做才算。

## §3 任务卡的固定结构

所有施工文档里的任务卡都长这样（后端卡与前端卡共用）。看到这个结构就知道每部分是干嘛的：

```markdown
### <卡号> · <标题>

`优先级` / `预计工时` / 依赖：<前置卡号> · **owner: backend**（前端卡写 `owner: frontend`——执行者同样是你）

**背景**
为什么要做这张卡。读完你应该知道"不做会怎样"。

**涉及文件**（白名单，规则 C4）
| 文件 | Grep 锚点 | 改法 |

**已经替你决定好的**（规则：不要自己发挥）
列出所有本可以权衡但已经定死的选择，以及定这样的理由。

**操作步骤**
1. 2. 3. …… 每步都是可执行的动作，不是目标描述。

**验收命令**（规则 C6）
```powershell
可直接复制粘贴的命令
```

**完成判据**
- [ ] 逐条可勾选，不含主观判断

**Commit**
```
给定的 commit message 模板
```
```

前端卡比后端卡多一个**可选**字段——只有含视觉工作的卡才写：

```markdown
**多模态环节**（Grok 辅助，规则见 GROK-FRONTEND-PLAYBOOK G6）
- 环节 1：视觉验收——完成后截屏核对渲染（正常/空/加载/错误态）
- 环节 2：图片粘贴区实现 + 自测（贴图、预览、清除）
```

有这一节的卡：**这一节交给 Grok**（§4），其余部分仍由你写、收口。

**"已经替你决定好的"这一节是 Composer 2.5 专用的。** 其他模型可能不需要，但对 Composer 2.5 它是必须的——没有这一节，它会在你没注意的地方做出一个看似合理但和整体架构冲突的选择。

## §4 和 Grok 的协作

| 你做什么 | Grok 做什么 |
|---|---|
| 主写全部代码：Python、schema、appserver、evals + Electron / React / TS UI | 只做前端卡里标注的「多模态环节」：截屏视觉验收、图片类 UI、对照设计稿 |
| **合并** `schema.json` 后生成 TS 类型 | 类型从合并后的 schema 生成（G3），不手写平行类型 |
| 定义协议方法（查询 / 会话 / 工具审批的契约） | 只调用契约里有的方法 |
| 收口 Grok 的产出（并入你的分支、统一 commit） | 产出交回，不另开分支 |

**委托模板**（前端卡有「多模态环节」字段时用）：

```
请做 <卡号> 的「多模态环节」：
1. 环节边界：<列明环节里的事，只做这些>
2. 交付物：<代码片段 / 截图对比 / 问题清单>
3. 验收：<tsc / vitest / 起 dev server 后截屏核对>
4. 产出交回我收口，不要另开分支
```

联调失败时：**先看是契约错了还是渲染错了**。两者都是你的卡，但视觉类问题可以让 Grok 看图定位、贴图说明哪里不对，你再修。

Grok 查回来的外部资料若影响后端卡，**落进施工文档**再开卡——下一个 Composer 会话看不到聊天记录。

需要外部资料时，按 [`GROK-FRONTEND-PLAYBOOK.md`](./GROK-FRONTEND-PLAYBOOK.md) §5 的模板请 Grok 查，**模板只维护在那一处，不要在这里复制**。

## §5 会话开场白模板

每次开新会话做一张卡，用这个模板起头。它把上面的规则压缩成一段可以直接粘贴的话：

```
读 docs/plans/opus5-plan/MODEL-ASSIGNMENT.md §0，再读 COMPOSER-2.5-PLAYBOOK.md 的 §2。

本次任务：<文档路径> 的 <卡号> 这一张卡，只做这一张。owner: backend（前端卡：owner: frontend——执行者同样是你）。

要求：
- 用卡里的 Grep 锚点定位，不要信行号
- 只改卡里"涉及文件"表列出的文件
- 卡里"已经替你决定好的"部分不要自己发挥
- 前端卡标了「多模态环节」的，那一节按 §4 模板交给 Grok，其余你写并收口
- 验收命令全部跑通再说做完
- 卡住了按 C8 停下来报告，不要猜

开始前先把这张卡完整读一遍，然后告诉我你的执行计划（不超过 5 步），我确认后你再动手。
```

**最后一句是关键**。让它先说计划、你确认了再动手，能拦住绝大部分跑偏——因为跑偏在计划阶段就看得出来，等它改完十个文件再看就晚了。

## §6 常见失败模式与预防

这些是 Composer 2.5 在这类项目上最容易出的问题。施工文档已经针对性地做了防护，这里说明防护的原理，方便你 review 时知道该盯哪里。

| 失败模式 | 长什么样 | 文档里的防护 |
|---|---|---|
| **静默扩大范围** | diff 里出现卡里没提过的文件 | C4 白名单 + review 时先看 `git diff --stat` |
| **改测试让它变绿** | 测试断言被改宽松了 | 验收命令里包含"基线对比"；review 必看测试文件的 diff |
| **发明不存在的 API** | 调用了一个看起来该有但实际没有的函数 | 卡里给出真实的 API 签名，不让它推断 |
| **行号漂移改错位置** | 改了相邻的无关函数 | C3 Grep 锚点 |
| **一张卡做成三张** | 顺手把后面的卡也做了 | C1 + commit 粒度检查 |
| **"我觉得这样更好"** | 偏离卡里定好的方案 | "已经替你决定好的"小节 + 写明理由 |
| **卡住了硬试** | 同一个错误改五遍 | C8 三次法则 |
| **视觉环节硬做** | 多模态环节没用 Grok，自己"猜"UI 长什么样 | C7 + §4 委托模板 |
| **忽略警告** | lint warning 留着不管 | 验收命令里 `ruff check` 必须零输出 |

### Review 清单（每张卡合并前过一遍）

```powershell
git diff --stat            # 文件数对不对？有没有卡外文件？
git diff -- '*test*'       # 测试是被加强了还是被改松了？
git log --oneline -1       # 是不是一个卡一个 commit？
```

三条都对，再看具体实现。前端卡额外确认：标注的多模态环节确实交给了 Grok，且产出已并入。

## §7 两个项目的差异

本手册两个项目共用，但有两处不同：

| | RxyCode | LinkAgent |
|---|---|---|
| **仓库** | `D:\agent-demo\RxyCode\RxyCode1_1_0` | 新建独立仓库 |
| **改动性质** | 在 3700 行的 `agent_v2.py` 等存量代码上手术 | 大部分是新代码 + 集成既有研究代码 |
| **最大风险** | **回归**——改坏了现有功能 | **集成错位**——两边的抽象对不上 |
| **每张卡的额外验收** | `evals` 基线对比（证明没回归） | 契约测试（证明两边接口对得上） |
| **文档入口** | [`rxycode/README.md`](./rxycode/README.md) | [`linkagent/README.md`](./linkagent/README.md) |

**RxyCode 的存量代码不许因 LinkAgent 而改**——这是 LinkAgent 项目成立的前提。LinkAgent 里任何一张卡如果需要改 RxyCode 的源码，都属于 C8 的"停下来报告"情形。

## §8 一句话总结

**一次一张卡（后端或前端都主写），用 Grep 定位，只碰白名单，不做设计决策，多模态环节委托 Grok 并收口，验收全绿才算完，卡住就停下来问。**
