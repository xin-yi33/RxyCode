## §1 这份文档是什么/不是什么

**是**:一份"论文 → RxyCode"的翻译和取舍笔记。你回头想搭这块积木时,不用重读一遍论文,读这份就知道该从哪儿下手。

**不是**:实现计划。没有任务卡、没有工时、没有验收命令。Phase A–E 是照着做就能做完的施工图,这份不是。

**为什么现在写**:论文里有大量**负面实测结果**,它们的价值不在于"这个方案不行",而在于**告诉你哪些工作根本不用做**。这些信息如果不记下来,一年后你会把它们再踩一遍。§3 是本文档的核心。

## §2 论文速览(工程视角)

### 2.1 核心抽象:EKO

论文把管理单元定义为 **Executable Knowledge Object**:

```
s = (id, path, desc, pre, proc, deps, conflicts, params, scope,
     version, status, provenance, evidence, confidence_evidence,
     confidence, stats)
```

关键点:
- `id` 跨版本稳定
- `conflicts` 是**对称**的(A 列了 B,B 必须列 A;单向边会被事务性修复)
- `confidence` 从 `confidence_evidence` 推导,不是直接写的
- `stats`(执行结果)独立存,**不影响 confidence**
- 安全是创建 Agent 时固定的外部约束,**不是一个可变的普通 EKO**

EKO 明确区分于两样东西:**原始 tool**(有能力但没有生命周期元数据)、**episodic memory**(有记录但不可直接执行)。

### 2.2 五个机制

| 编号 | 机制 | 一句话 |
|---|---|---|
| C1 | 森林索引 | 按 domain 分区 + 有序复合键 `(path, scope, version, status)`,限制暴露给模型的候选数量 |
| C2 | PCDR | 从路径和显式依赖里恢复出拓扑合法的完整执行计划;歧义时把**完整候选路径**摆给用户选,而不是列技能名 |
| C3 | 确定性冲突消解 + SAG | 五级优先级 `安全 > 显式指令 > 任务上下文 > 个人 > 默认`;SAG 是**纯代码、零 LLM、零 token** 的激活前闸门,输出 killed / warning / safe |
| C4 | 双通道经验演化 | Mode U(用户交互反思)学"用户想要什么";Mode A(AED)从**已验证的可观测轨迹**学"agent 怎么把事做成";两条通道原始证据**永不融合** |
| C5 | 全系统质量-成本 | 把能确定性处理的决策从 LLM 移到管理层,看整体划不划算 |

### 2.3 几个值得记住的细节

**置信度**:手写/导入/遗留 Skill 起始 0.50。Beta(2,2) 更新:`confidence = (2 + S) / (4 + S + N)`。证据 ID 幂等,**无时间衰减**,执行统计和 LLM 冲突判断都不改 confidence。

**生命周期迟滞**(防阈值震荡):active 掉到 0.40 以下 → deprecated;deprecated 要回到 0.50 才能成为 candidate 重新验证。**deprecated 不是删除**,不参与普通规划但物理保留,可通过后续用户证据恢复。

**隐式记忆门槛**:同一情境下、来自**不同任务**的**至少三条一致证据**才激活。显式记忆(用户明说"记住")立刻创建。

**AED 的硬约束**:只读可观测轨迹(`任务上下文 → 状态 → 动作/工具调用 → 观测 → 失败 → 修正 → 已验证的成功结果`),**严禁使用隐藏 CoT**,必须经过 replay 或沙箱验证才能激活,单次成功不自动晋升。

**同优先级平局**:`confidence → Wilson 95% 下界(z=1.96) → 样本数 → 平均延迟 → 用户澄清`。完全平局**必须澄清,不许隐式选一个**。

## §3 论文自己测出来的结论(含负面)

> **这一节是整份文档的核心。** 论文最有价值的地方不是它证明了什么,而是它**诚实地报告了什么没成立**。这些负面结果直接决定落地顺序。

### 3.1 全系统结果

| 条件 | 成功率 | 计划完整度 | 探针准确率 | 平均 token | 延迟 |
|---|---:|---:|---:|---:|---:|
| Pure LLM + 全工具表 | 11.4% | 71.8% | 61.0% | 14,241 | 7,665 ms |
| Flat 检索 + LLM planner | 10.5% | 66.6% | 61.0% | 5,312 | 7,416 ms |
| DAG 知识库 + 独立 Skills | 10.1% | 69.5% | 59.0% | 10,742 | 8,961 ms |
| **Full SkillForest** | **22.7%** | **92.8%** | **100%** | **4,743** | **4,811 ms** |
| 去掉 SAG | 9.8% | 63.7% | 58.0% | 4,794 | 7,403 ms |

成功率翻倍、计划完整度 +21pp、token **降 66.7%**、延迟降 37.2%。

### 3.2 但 Shapley 分解把话说死了

八个组合全跑了一遍,三个组件的平均边际贡献:

| 组件 | Shapley 值 |
|---|---:|
| **SAG** | **+0.445** |
| PCDR | **+0.000** |
| 经验演化 | **−0.014** |

**几乎全部收益来自 SAG。** PCDR 的端到端边际效应是**零**,经验演化是**负的**。

这不是说 PCDR 没用——RQ2 单独测它是 90.8% vs 孤立检索 19.2%,组件层面效果极强。但 RQ6 的配对消融(共享同一份 planner 原始输出,只加确定性依赖补全)显示它在那个任务分布上**没有额外的端到端增益**。

**工程含义**:PCDR 只在依赖元数据密集、任务真的多步强依赖时才回本。任务分布不对,它就是白写的。

### 3.3 逐条负面结果

| 机制 | 论文实测 | 工程含义 |
|---|---|---|
| **森林路由** | Recall@10 **0.533 vs 平铺 TF-IDF 0.667(−13.4pp)**。候选暴露 −68.3%,延迟 −46.1%。论文明说:**<1,000 个技能时平铺检索更好** | RxyCode 用户的 skill 量级是几十到几百。**别建森林索引** |
| **oracle 澄清** | 注入正确 domain 后 Recall@10 从 0.533 变成 0.537,**基本没变** | 路径澄清救不回路由错误。别指望这条 |
| **语义冲突检测** | 17,810 个社区 skill 抽 500 对,人工标注只有 **6 对真冲突(1.2%)**。最好的模型 Macro-F1 0.538,**冲突 precision 只有 8.1%**,三个模型分别产生 227/131/68 个假阳性 | **真冲突极其罕见,而且 LLM 严重过度预测。别做 LLM 冲突检测** |
| **AED** | 同域成功率 62.5%,高于无经验 50%,但**低于持久化轨迹缓存的 75% 和手写 skill 的 75%**。两次运行分别是 25% 和 100%,**波动 75pp**。prompt 字符数 774 vs 缓存 293 | **朴素蒸馏打不过一个简单的成功轨迹缓存**。这条直接修正了 Phase E 的假设 |
| **AED 跨域** | 强制跨域激活:成功率 50%(无经验是 75%),token 从 558 涨到 878 | **负迁移是真的**。域门控不是可选优化 |
| **Mode U** | 偏好摘要 F1 从 0.10 提到 0.20–0.23,跨会话恢复/撤销 100%。但**留出集选择重合度基本没变** | 能提取偏好、能管住生命周期,**但没证明能改善最终决策** |
| **SkillForest 索引 vs 裸 SQLite** | 前缀扫描 11.15ms vs 13.04ms,更新 0.024 vs 0.027 ms/op。**同一个数量级** | 论文自己说:只要有序持久化访问的话,**thin SQLite 基线就够了** |
| **SAG 对抗样本** | 声明规则域内 36/36 全过、0 假阳性。域外 27 个变体总准确率 **55.6%**,其中多语言 / 间接指代 / prompt 注入 / 分步诱导 **全部 0%** | SAG 是**低成本低误报的基线过滤器**,不是安全系统。别当安全方案卖 |
| **鲁棒性** | 8 类扰动里严格状态恢复只有 2/3。损坏版本回滚"安全拒绝但没恢复到目标版本" | 回滚链有真实缺口 |

### 3.4 一条容易被忽略的成本细节

SAG 相对"无 SAG"省 token 只有 **1.1%**(4,743 vs 4,794)。省的原因不是 SAG 便宜,而是**被拦下的任务根本不调 planner**。也就是说 SAG 的成本优势有相当一部分来自"短路",在低风险任务分布上会明显缩水。

而它 +12.9pp 的成功率提升,来自"该拦的拦住了 = 判对了"。**在 RxyCode 的日常编码任务里,killed 类内容的自然发生率接近零**,所以不要指望复现这个数字。

## §4 RxyCode 现在在哪

### 4.1 现状对照

RxyCode 已有的 skill 系统:

| 模块 | 位置 | 干什么 |
|---|---|---|
| `skill_manager` | `tools/skill_manager.py` | 从 GitHub 搜索/下载/安装/卸载,存 `~/.rxycode/skills/<name>/SKILL.md` |
| `skill_tool` | `tools/skill_tool.py` | `skill(name)` 工具,读 SKILL.md 返回**整段文本** |

**这套东西大致对应论文的 "Flat 检索" 或者更弱的基线**:平铺列表、无元数据、无依赖、无版本、无生命周期、无冲突消解、无激活前闸门。而且它连"检索"都算不上——LLM 必须自己猜出 skill 名字才能调。

**好消息**:文件层面的安全做得很扎实,不用重做。ZIP 路径穿越校验(`:67-81`)、成员类型校验(`:84-92`)、解压炸弹防护(`:95-133`,压缩比上限 200、总量上限 100 MB)、原子发布(staging + `os.replace`,`:293`)、名称白名单(`:51`)。

### 4.2 已经存在的地基

| 论文要的 | RxyCode 已有的 | 缺口 |
|---|---|---|
| 双记忆边界(episodic evidence vs Active Skill Store) | `memory/`(短期/长期/用户记忆/会话存储)+ `~/.rxycode/skills/` | **物理边界已经在了**,但没有"原始记录不得直接当 skill 调度"这条规则——因为现在压根没有东西在调度 skill |
| SAG 激活前闸门 | `core/safety/`(风险等级、审批、写白名单、审计) | **形状高度吻合**。SAG 可以做成 `core/safety/policy.py` 的一个扩展,而不是新系统 |
| 有序持久化后端 | 无 | 但论文说 thin SQLite 就够,几十个 skill 更是连 SQLite 都不需要 |
| 五级优先级 | 无(但 `core/governance.py` 有 `ModelRole`/`ModelRouter` 的雏形) | 需要新写,但很小 |
| 已验证的成功轨迹(AED 的输入) | **Phase B 的机械验证门 + `VerdictRecord`** | 见 §7,这是最漂亮的一处吻合 |
| 生命周期状态机 | 无 | `candidate → validated → active → deprecated` |

## §5 落地设想:四层,按实测收益排序

> **顺序直接照抄 §3.2 的 Shapley 值和 §3.3 的负面结果。** 不要按论文的章节顺序做。

### 第 1 层 · SAG(Shapley +0.445,论文里唯一有明确正收益的组件)

**做什么**:把论文的 SafetyPolicyChecker 接进 `core/safety/`,作为 skill 激活前的闸门。

- 三分类 killed / warning / safe
- 7 类 FULL 规则 + 9 类 PARTIAL 规则
- **纯代码,零 LLM,零 token**——这是它能赢的根本原因
- warning 可以 `accept_risk()`,标记为 `user_accepted_risk`
- FULL 不可覆盖

**为什么第一个做**:成本最低(几百行正则 + 一张规则表)、收益实测最高、而且能复用 RxyCode 已有的安全审批 UI(TUI/SSE approval 已经有了)。

**但要诚实**:论文的 +12.9pp 成功率提升,是因为 RQ6 的探针里刻意放了 25% killed + 25% warning。RxyCode 的真实编码任务里 killed 内容接近零。**SAG 在 RxyCode 的真实价值主要是防"下载来的恶意 skill"**,不是提升任务成功率。这正好接上 Phase E 的 E5(信任边界)。

**规模**:小。几百行 + 一张规则表 + 一套测试。

---

### 第 2 层 · 元数据 + 生命周期(便宜,且是后面一切的前提)

**做什么**:

1. **skill frontmatter**——就是 Phase E 的 E1,已经规划好了
2. **置信度**:`confidence = (2 + S) / (4 + S + N)`,起始 0.50,证据 ID 幂等,无时间衰减
3. **状态机**:`candidate → validated → active → deprecated`,加迟滞(<0.40 降级,≥0.50 才能重新验证)
4. **不物理删除**:deprecated 保留,可恢复
5. **provenance + 版本链**:就是 Phase E 的 E5

**为什么第二**:代码量很小(Beta 更新是一行公式,状态机是十几行),但它是 persona、冲突消解、经验演化全部的前提。而且它自己就有用——"这个 skill 我用了三次都不好,自动降级"是实打实的体验改善。

**别做的**:
- ❌ **森林索引**。论文自己说 <1,000 技能平铺更好,而且森林路由掉 13.4pp recall。RxyCode 用户装几十个 skill,平铺列表 + frontmatter 完全够
- ❌ **B+ 树 / 自定义有序索引**。论文实测和 thin SQLite 同一个数量级。真到需要持久化的那天,直接上 SQLite

**规模**:小到中。

---

### 第 3 层 · 五级优先级(便宜,确定性,零 token)

**做什么**:`安全 > 显式指令 > 任务上下文 > 个人 > 默认`。

在 RxyCode 里的映射:

```
安全         core/safety/ 的策略 + SAG          不可覆盖
显式指令     用户当前这句话 / 斜杠命令
任务上下文   当前 session 的任务约束
个人         persona / active skill 的偏好
默认         config/settings.py
```

**同优先级平局**照抄论文:`confidence → Wilson 95% 下界 → 样本数 → 平均延迟 → 用户澄清`。**完全平局必须问用户,不许隐式选一个。**

**别做的**:
- ❌ **LLM 语义冲突检测**。论文实测真冲突只占 1.2%,而且最好的模型 conflict precision 只有 8.1%——它会把工具差异、流程顺序、表面相似全判成冲突。**为 1.2% 的场景付出 68–227 个假阳性,不值**
- 真需要的时候,论文的做法值得抄:LLM **只返回 `is_conflict`,绝不选赢家**,赢家由确定性代码定;判断结果按 `(稳定 ID, 版本, 内容哈希, 行为规格)` 缓存;模型失败**绝不当作"兼容"**,而是让计划挂起

**规模**:小。

---

### 第 4 层 · 经验演化(风险最高,收益最不确定)

**这一层要改论文的做法。**

论文的 AED 输给了持久化轨迹缓存(62.5% vs 75%),而且波动 75pp。所以:

```
第 4a 步  先做持久化成功轨迹缓存(简单、便宜、论文里它赢了)
            ↓
第 4b 步  跑评测。缓存到底带来多少收益?
            ↓
第 4c 步  只有当缓存的收益够明显、且它的上下文开销明显是瓶颈时,
          才去做 AED 蒸馏——而且必须以缓存为基线做 A/B
```

**这条直接修正 Phase E 的 E3/E4。** Phase E 假设"采集数据 → 蒸馏"是自然路径,论文的数据说:**先证明缓存有用,再谈蒸馏**。

如果真要做 AED,论文的约束一条都不能省:

| 约束 | 为什么 |
|---|---|
| 只读可观测轨迹 | 隐藏 CoT 严禁使用 |
| 必须有已验证的成功结果 | 单次成功不自动晋升,要过 replay 或沙箱 |
| 必须带域适用条件 | 强制跨域激活实测掉到 50%,低于无经验的 75% |
| 必须可停用、可回滚 | 不需要用户确认,但必须可撤销 |
| 与 Mode U 的原始证据**永不融合** | 两条通道独立触发、独立激活、独立回滚 |

**Mode U 和 Mode A 的分工**照抄论文:同一字段冲突时**用户通道优先**,不同字段可以组合。

**规模**:大。而且是四层里唯一可能白干的一层。

## §6 最大的概念落差:EKO 在 RxyCode 里到底是什么

**这是落地时第一个必须回答的问题,现在没答案。**

论文的 EKO 有一个 `proc` 字段——**可调用的过程**。RxyCode 的 skill 是一份 `SKILL.md`,是**给 LLM 看的自然语言指令**。两者的"可执行"不是一回事。

我的落地假设(**只是假设,回头要验证**):

```
RxyCode 的 EKO = 三样东西的联合体 + 一层治理元数据

  ① prompt 片段    ← 现在的 SKILL.md 正文
  ② 工具集绑定     ← Phase B 的 AgentSpec.tools
  ③ SOP 片段       ← Phase B 的 SopStage 序列

  + 治理元数据:path / scope / version / status /
                provenance / confidence / deps / conflicts
```

如果这个假设成立,那么:

```
Persona = 在某个 domain 下,一组 active EKO 解析出来的 AgentSpec
```

也就是说 **PersonaAgent 不是一个新运行时,而是 `AgentSpec` 的一种生成方式**——这正是 Phase E §3.1 已经得出的结论,论文从另一个方向印证了它。Phase E 的 E6(证明 `AgentSpec` 可以脱离文件系统程序化构造)就是为这一步留的门。

**这个假设最大的风险**:论文的 PCDR 依赖 `requires` / `composes` 这类**显式声明的依赖边**。而 RxyCode 的 skill 是从 GitHub 下载的第三方 markdown,**它们之间没有任何声明的依赖关系,也不太可能有**。

→ **PCDR 在 RxyCode 大概率无从下手**,除非依赖关系由 SOP(Phase B 的 `SopStage.next_on_success`)来承载,而不是由 skill 之间的边来承载。这也正好解释了论文里 PCDR 为什么 Shapley 是 0:它需要的元数据密度,现实里很难有。

## §7 与 Phase A–E 的接口对应

### 7.1 已经给到的地基

| 论文要的 | 来自 | 说明 |
|---|---|---|
| **已验证的成功轨迹**(AED 的唯一合法输入) | **Phase B 的机械验证门 + `VerdictRecord`** | 这是最漂亮的一处吻合。论文说 AED 必须"经测试或环境状态验证"才能激活,而 Phase B 的机械验证门(文件存在、AST 可解析、lint 干净、测试通过、diff 非空)**恰好就是这个验证**。审计结论绑定 diff sha256 更是直接给了"这份轨迹到底成没成"的客观答案 |

| 双记忆边界 | `memory/` + `~/.rxycode/skills/` | 物理边界已在,缺的是"原始记录不得直接调度"这条规则 |
| skill 元数据 | **Phase E 的 E1** | frontmatter,已规划 |
| provenance + 信任 | **Phase E 的 E5** | `SkillProvenance` + `content_sha256` 篡改检测,已规划 |
| 质量信号采集 | **Phase E 的 E3 / E4** | `QualitySignal.is_gold` 就是论文说的"已验证成功" |
| `AgentSpec` 可程序化构造 | **Phase E 的 E6** | Persona 生成 AgentSpec 的门 |
| 运行时替换工具集 | **Phase B 的 `_build_scoped_registry`** | Phase E §6.1 已经标了:如果 persona 要改工具集,B4 就该设计成可运行时替换 |
| 用户级团队目录 | **Phase B §7 预留的 `~/.rxycode/teams/`** | Persona 的团队定义放这里 |
| 结构化输出能力位 | **Phase A 的 `structured_output`** | EKO 抽取需要模型能出结构化结果;论文里 Doubao 有 4.5% 无效 JSON,这条很实在 |

### 7.2 要回头修正 Phase E 的两处

| Phase E 原来的假设 | 论文的数据 | 该改成 |
|---|---|---|
| E3/E4:采集数据 → 蒸馏是自然路径 | AED 62.5% **输给**轨迹缓存 75%,且波动 75pp | **先做缓存基线,蒸馏必须以缓存为对照**。见 §5 第 4 层 |

**这两条现在不用改 Phase E 的文档**——E 的六张卡本身是对的(埋点、元数据、信任边界都要做)。要改的是"埋完点之后干什么"的预期。等真要动这一层了再回来改。

## §8 现在就能借走的东西(评测方法论)

**论文的实验设计比它的系统设计更值得马上抄。** 这部分和 PersonaAgent 无关,可以现在就用在主计划 Phase 1 的 evals harness 上。

| 方法 | 怎么用在 RxyCode |
|---|---|
| **2ⁿ 组合全跑 + Shapley 分解** | 这就是论文能发现"PCDR 边际贡献是 0"的原因。RxyCode 的 Phase B 有多 Agent / 机械验证 / 审计三个开关,Phase C 有多模型 / pair-program / 仲裁——**正好可以做同样的立方体消融**,而不是只跑"全开 vs 全关" |
| **配对消融共享原始输出** | 论文里 PCDR-on 的组合**复用** PCDR-off 的 planner 原始输出,只叠加确定性补全,这样 toggle 就不含模型采样噪声。RxyCode 测机械验证门时可以照做 |
| **固定受控序列** | 100 条 13 任务的固定序列,覆盖普通检索、多步依赖、重复偏好、偏好纠正、生命周期回滚、确定性冲突、安全边界、跨域边界、跨会话复用。**这个清单可以直接改造成 RxyCode 的 evals 任务模板** |
| **runtime–scoring 隔离** | executor 拿到的对象里不含任何 `gold_*` / `expected_*` 字段,打分器在模型调用全部结束后才读标签。**改标签不许改变 prompt、预测、token、调用次数**——这条应该写进 RxyCode 的 evals 契约 |
| **失败留在分母里** | 4.50% 的无效响应全部计入分母,不重跑不剔除 |
| **Wilson 95% 下界做排序** | 小样本下比裸成功率稳,RxyCode 的 evals 排序可以用 |
| **预注册阈值** | 每个 RQ 事先写死"达不到什么就算这个机制不值得"。例如 C1 是"成功率掉超过 2pp 且上下文缩减不到 30% 就不值"。**这个习惯比任何单项技术都值钱** |

§8 这一整节可以脱离 Phase F 独立执行,和 PersonaAgent 做不做无关。

## §9 我的疑虑

按我认为的严重程度排:

**1. 绝对成功率太低。** Full SkillForest 22.7%,Pure LLM 11.4%。相对提升翻倍很漂亮,但绝对值意味着这个任务分布上**四次里有三次是失败的**。这个量级的系统放进 RxyCode,用户感知到的可能不是"变强了"而是"多了一堆看不见的机制,还是不好使"。落地前要先确认 RxyCode 的任务分布上基线成功率在什么水平。

**2. SAG 的收益在 RxyCode 会缩水。** 论文的 +12.9pp 来自刻意配置的 25% killed + 25% warning 探针。日常编码任务里这两类接近零。SAG 在 RxyCode 的真实价值是**防恶意 skill**(Phase E 的 E5 场景),不是提升任务成功率。别拿论文的数字给自己画饼。

**3. PCDR 在 RxyCode 可能无从下手。** 见 §6。第三方 markdown skill 之间不会有声明的依赖边。这块要么放弃,要么把依赖关系挪到 SOP 层(Phase B 已经有了)。

**4. AED 现在还没跑通。** 论文自己的结论就是"验证了可以持久化、可域门控、可回滚,但没验证有本地收益"。这是四层里唯一可能白干的。

**5. 生命周期治理缺自动清理。** 论文明说没有时间衰减和物理删除,"长期运行下控制技能膨胀的能力有待验证"。个人 agent 跑三年之后几千个 deprecated skill 怎么办,论文没答案。这个问题 RxyCode 会更早遇到,因为 skill 是从 GitHub 批量下载的。

**6. 隐藏的心智成本。** 五级优先级 + 置信度 + 迟滞 + 双通道 + 域门控——用户遇到"agent 为什么这么做"的时候,要解释清楚需要展示一条很长的推理链。论文有 provenance 和 audit log,但**没有讨论怎么把它讲给用户听**。RxyCode 要做这一层,UI 的工作量可能比后端还大。

## §10 什么时候值得启动

**触发条件(全部满足才考虑)**:

1. 主计划 Phase 0–3 + Phase A/B/C/D 都做完了
2. Phase E 的六张预留卡做完了,而且 **E4 给出的"金标准样本比例"不低于 10%**——低于这个数,经验演化那一层没有原料
3. 用户真的开始装 skill 了,而且**装到了几十个以上**——一两个 skill 不需要生命周期治理
4. 有人抱怨过"agent 记不住我的偏好"或者"装了 skill 之后反而变差了"——**没有这个抱怨就说明还不痛**

**启动时的第一步不是写代码,是**:

用 §8 的方法论,在 RxyCode 自己的任务分布上跑一遍**基线**:
- 现在的平铺 skill 系统,成功率是多少?
- 装 10 / 50 / 200 个 skill,上下文和成功率怎么变?
- 用户偏好被重复问了多少次?

**拿到这三个数字之前,不要动手。** 论文最值得学的地方就是它先测再下结论,而且敢把负面结果写在正文里。

## §11 一句话总结

论文验证了**SAG 这一个组件确实有明确正收益**,森林索引、PCDR、经验演化三块在实测里分别是"小库不划算"、"边际为零"、"输给一个简单缓存"。

**所以 SkillForest 在 RxyCode 的落地不是一个 5 万行的系统,而是四层里的前两层**:一个纯代码的激活前安全闸门,加一套 skill 元数据和生命周期。这两层加起来量级不大,而且都能挂在 RxyCode 已有的模块上(`core/safety/`、`tools/skill_manager.py`)。

后两层等有了真实数据再说。
