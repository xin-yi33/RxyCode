# 工程顺序 · 两个 agent 窗口怎么把两个项目跑完

> **这份文档回答**：开两个 Composer 窗口并行干活，哪些卡能同时飞、哪些必须排队、怎么不互相踩。
>
> **它不替代施工文档。** 做什么看 [`rxycode/`](./rxycode/README.md) 和 [`linkagent/`](./linkagent/README.md)，怎么干活看 [`COMPOSER-2.5-PLAYBOOK.md`](./COMPOSER-2.5-PLAYBOOK.md)。**这里只管顺序、并行度和冲突。**
>
> **创建**：2026-08-01

---

## §0 结论先说

**总量是 90 张卡**（RxyCode 30 + LinkAgent 60，不含 RxyCode Phase A/B/C/D）。

**瓶颈不是 agent 的产出速度，是你审查的速度。** 所以：

| 直觉 | 实际 |
|---|---|
| 开两个窗口 = 两倍产出 | **约 1.3–1.6 倍。** 审查只有你一个人做，是串行的 |
| 开三个窗口更快 | **基本没用。** 你审不过来，第三个窗口只会积压 |
| 双开的价值是并行执行 | **双开的真正价值是：你审 A 的时候 B 在跑。** 把 agent 的执行时间藏进你的审查时间里 |

**推论决定了整份文档的排法**：不按日历排，按**"哪两张卡能同时在飞且不打架"**排。

**唯一值得优先投入的加速手段是自动化验收**——它是唯一能放大你审查带宽的东西。这也是为什么 RxyCode 的 **Phase 1（让评测说真话）必须排在所有扩展之前**：没有可信的自动信号，你就得逐行读 agent 的产出，那才是真正的天花板。

## §1 单位换了：不是人周，是卡

原来按"人周"排是因为假设人在写代码。现在写代码的是 agent，人周这个单位失效了。

**新的计量单位是"卡"**，因为一张卡 = 一个 commit = 一个你要审的单元（[Playbook C1](./COMPOSER-2.5-PLAYBOOK.md)）。

| 项目 | 卡数 | 其中"大卡"（agent 单次跑不完、要拆） |
|---|---:|---|
| RxyCode Phase 0 | 8 | — |
| RxyCode Phase 1 | 6 | H3（修坏任务） |
| RxyCode Phase 2 | 8 | **P3（抽 Session 层）** |
| RxyCode Phase 3 | 8 | D2、D3 |
| LinkAgent L0–L9 | 54 | **L5-3（AED 蒸馏）**、L9-5 |
| LinkAgent L10（横切） | 6 | — |
| **合计** | **90** | 6 张 |

> **L10 不是一个阶段，是横切的六张卡**，分散插在 L1~L5 之间，见 [`L10 §3`](./linkagent/L10-SKILL-INTEROP.md) 的排期表。其中 **L10-4 是止血卡**（RxyCode 默认注册的 `skill` 工具能绕过全部治理），排期见 §4 阶段 3。

**施工文档里写的"工时"（如 L5 = 8.5 天）是人的工时，现在只能当作"这张卡有多复杂"的相对指标读，不要当日历用。**

### 怎么估真实进度

单卡从开工到合并的时间 ≈ **agent 执行 + 你审查 + 修一轮**。前者几分钟到几十分钟，后者取决于卡的大小和你的熟悉程度。

**跟踪进度用"已合并卡数 / 90"，不要用日期。** 跑完前 10 张卡之后你会有自己的速率，那时候再推算完成时间才有意义。

## §2 真正的三个约束

人力和技能都不再是约束了（agent 写 Python 和 TS 一样）。剩下三个：

### 约束 ① 依赖链（硬，改不了）

这四条是**语义依赖**，不是资源冲突，加窗口也解决不了：

| # | 依赖 | 违反的后果 |
|---|---|---|
| ① | **LinkAgent L2 ← RxyCode Phase 2** | Phase 2 改 `AgentV2` 对外形态，桥接层要跟着改 |
| ② | **LinkAgent L9-4~L9-8 ← RxyCode Phase 3** | 桌面端 fork Phase 3 的 Electron 壳，没壳可 fork |
| ③ | **LinkAgent L5 ← L3 完成并验证** | 论文实测：作用域没修就开反馈演化，DeepSeek 上是**净负收益 −2.69 pp**。做反了会变差，不是"最好先做" |
| ④ | **一切 ← RxyCode Phase 1** | 没有可信评测，你无法判断 agent 的产出有没有搞坏东西 |

> ①② 在 §6 里会重新评估——**返工变便宜之后，这两条的约束力比原来弱**。③④ 不受影响，它们是语义约束。

### 约束 ② 文件冲突（这才是双开的主要风险）

两个 agent 同时改同一个文件 = 后合并的那个把前一个覆盖掉，而且**两边的验收都会通过**（各自跑的时候都是对的）。

**这类问题不会报错，只会静默丢代码。** 防它的唯一办法是提前把文件所有权划清楚——见 §4。

### 约束 ③ 审查带宽（真正的天花板）

见 §0。**你能审多快，整个项目就能跑多快。**

三个能放大它的投入，按性价比排序：

| 投入 | 效果 |
|---|---|
| **RxyCode Phase 1（评测说真话）** | 最高。有了可信基线，你审的是"基线有没有掉"，不是"这 300 行对不对" |
| **每张卡的验收命令写死在文档里** | 已经做了。agent 必须贴真实输出，你先看输出再看 diff |
| **契约测试**（L2-1、L9-1 的超集测试） | 跨仓库变更会自动报警，不用你记着 |

## §3 两条泳道：按仓库划，不按技能划

**最干净的双开方式是：一个窗口在 RxyCode 仓库，一个窗口在 LinkAgent 仓库。**

```
窗口 1 ── D:\agent-demo\RxyCode\RxyCode1_1_0    ← RxyCode 全部
窗口 2 ── D:\agent-demo\LinkAgent               ← LinkAgent 全部
```

**两个不同的 git 仓库，文件冲突概率为零。** 这是最省心的配置，能用就用它。

### 什么时候会被迫同仓双开

只有一种情况：某个阶段一条泳道空了，你想让它去帮另一条。这时用 **git worktree**，两个窗口各自一个分支和工作目录，通过 PR 合并——**不要两个窗口开同一个工作目录**。

同仓双开的文件所有权规则见 §4 各阶段的表。

## §4 分阶段执行顺序

### 阶段 0 · 开局（RxyCode Phase 0 ‖ LinkAgent L0+L1）

**两条泳道从第一天就能同时跑，零依赖、零冲突。**

| 窗口 1 · RxyCode | 窗口 2 · LinkAgent |
|---|---|
| **Phase 0** S1–S8（8 张） | **L0** 建仓与骨架（5 张） |
| 止血：lint、CI、CORS、死文件 | **L1** EKO 核心移植（6 张） |
| — | 从 SkillForest 搬代码，用冻结语料验证搬对了 |

**为什么能并行**：不同仓库；LinkAgent L0/L1 完全不 import RxyCode。

**这一段做完的标志**：`ruff check .` 进 CI；LinkAgent 能 `pip install -e .`、冻结语料契约测试全绿。

---

### 阶段 1 · 评测先行（RxyCode Phase 1 ‖ LinkAgent 待命）

> **这是整个计划里最不该省的一段。** 它决定你后面所有卡的审查成本。

| 窗口 1 · RxyCode | 窗口 2 |
|---|---|
| **Phase 1** H1–H6（6 张） | **见下面"窗口 2 干什么"** |
| 让 evals 跑真实 Agent、修坏任务、进 CI、基线落盘 | — |

**窗口 2 干什么**：LinkAgent 的 L2 要等 Phase 2，这时候没有能推进的 LinkAgent 卡。三个选择：

| 选项 | 说明 | 推荐 |
|---|---|---|
| **先做 L10-2 / L10-5 / L10-1，再做 L8-2 / L8-3** | L10-2（Skill 解析器）**是 L8-2 的前置**——L8-2 不许自己写解析。L10-1/L10-5 只依赖 L1，都很便宜。L8-3 是**内容策展不是写代码**，16–25 条社区 skill 要逐条过 | ✅ **推荐**，而且这活早晚要干 |
| 空着 | 让你专心审 Phase 1 | 🟡 也合理，Phase 1 值得专注 |
| 去帮 RxyCode Phase 1 | H 系列卡之间有共享状态（评测任务集），并行改容易打架 | ❌ 不建议 |

> ⚠ L8-1（包格式与装载）里有一条校验依赖 L3 的 scope 模块，**这张卡留到 L3 之后**。先做 L10-2/L8-2/L8-3 不受影响。
>
> ⚠ **顺序别搞反**：L10-2 → L8-2 → L8-3。跳过 L10-2 直接做 L8-2，agent 会在 `curate.py` 里现写一套 SKILL.md 解析，之后 L10-3 再写第二套，两套解析产出的 EKO 结构就不一致了。

**出口标准**：`python -m evals.cli run --backend agent` 能跑真实 Agent，基线分数落盘。**从这里开始，每张卡合并前都要比对基线。**

### 阶段 2 · 协议（RxyCode Phase 2 ‖ LinkAgent 预置包）

Phase 2 是 **RxyCode Phase 3 和 LinkAgent L2/L9 共同的地基**，优先级最高。

| 窗口 1 · RxyCode Phase 2 | 窗口 2 |
|---|---|
| P1 定义协议层 | LinkAgent L8-2 / L8-3 收尾 |
| **P3 抽 Session 层**（最大的一张，考虑拆成 3–4 个 commit） | 或空着专心审 P3 |
| P4 appserver、P5 OpenTUI 迁移、P6 api_server 变薄、P7 P8 | — |
| P2 TS 客户端 | — |

#### 如果想让窗口 2 进 RxyCode 帮忙做 P2

P2（`frontend/protocol-client/`）和 P1/P3（`protocol/`、`core/session.py`）的文件集**确实不相交**，可以同仓双开。文件所有权：

| 窗口 | 独占 | 禁止碰 |
|---|---|---|
| 1（P1 P3） | `protocol/`、`core/`、`agent_v2.py` | `frontend/**` |
| 2（P2） | `frontend/protocol-client/` | `protocol/**`（**只读消费 `schema.json`**） |

**交接点只有一个**：`protocol/schema.json`。窗口 1 产出，窗口 2 从它生成 TS 类型。**在窗口 1 的 P1 合并之前，窗口 2 不要开工**——否则它生成的类型是过期的。

> 关于 **Phase A（模型适配）** 能不能塞进这里：文件集上确实和 Phase 2 不冲突（[主计划 §11.7](./rxycode/00-EXECUTION-PLAN.md) 分析过，接触面只有 `agent_v2.py` 的两处）。但**它会吃掉你审 P3 的注意力**，而 P3 是全项目最容易出错的一张卡。**建议 Phase A 推到后面**，不是因为做不了，是因为不值得在这时候分心。

**出口标准**：`protocol/schema.json` 已提交并有冻结测试；`python -m appserver` stdio 可跑通；OpenTUI 已迁到协议。

> 🚪 **这道门开了，LinkAgent L2 才能开工。**

### 阶段 3 · 两条主线全速（RxyCode Phase 3 ‖ LinkAgent L2→L6）

**这是并行收益最大的一段**，两条链都长、都在各自仓库、零冲突。

| 窗口 1 · RxyCode Phase 3（8 张） | 窗口 2 · LinkAgent（约 30 张） |
|---|---|
| D1 Electron 脚手架 | **L2** RxyCode 桥接（6 张） |
| D2 主窗口 | **L3** 情境化检索 + 作用域硬门（5 张）← 收益最大 |
| D3 流式 + 工具卡片 | **L4** 安全门控（4 张） → 紧接 **L10-4 止血**（1 张） |
| D4 审批 UI | **L5** 证据与反馈演化（6 张）← ⚠ 必须 L3 验证通过 |
| D5 设置页 | **L6** 依赖组合与冲突裁决（4 张，**默认关闭**） |
| D6 打包 / D7 自动更新 / D8 CI | **L8-1 / L8-4 / L8-5** 预置包接线（L3 之后） |
| — | **L7** 评测（5 张，可穿插）· **L10-3 / L10-6**（L5 之后） |

> **L10-4 为什么卡在 L4 正后面**：RxyCode 默认注册了 `skill(name)` 工具（`core/agent_v2.py:1499,1519`），它能把任意 `SKILL.md` 全文塞进上下文——**绕过 L3 的域门、L4 的安全门、L5 的证据链**。L4 一做完就有了 approval broker 的接线，这时候封成本最低。**在它之前，L3/L4 的治理效果都是可以被一句 `skill("xxx")` 抵消的。**

**跨域泄漏必须是 0。** 这是约束 ①③，不满足就回去修 L3，别硬上。

### ★ 决策点 · L7 首次基线

**这是整个计划里唯一一个"可能让后面全部作废"的地方。**

| L7-5 的结论 | 接下来 |
|---|---|
| **经验层有显著收益** | 做 L9 桌面端。这时 Phase 3 已完成，壳现成 |
| **无显著收益，但某个模块有** | 只留那个模块，砍掉其余；**不做 L9**，先把有效的部分做扎实 |
| **完全无收益** | **停 LinkAgent。** 两个窗口回 RxyCode Phase A → Phase B |

**必须真的准备好接受第三种结果。** 论文的 +5.27 pp 是在 100 条受控序列、两个特定模型、沙箱工具上测的，LinkAgent 的任务分布、工具、执行路径全都不同，而且**主动改了作用域机制**。[`APPENDIX-B`](./linkagent/APPENDIX-B-PAPER-EVIDENCE.md)：只能测，不能推。

同一轮还要跑 [`L8 §5`](./linkagent/L8-PRESET-EKO-PACK.md) 的四组对照。**如果"有预置包 − 无预置包"不显著，预置层要缩到最小甚至砍掉**，别因为已经做了就留着。

## §5 同仓双开的四条规则

只要两个窗口在同一个仓库，这四条必须守住。

### 规则 ① 先划文件所有权，再开工

开第二个窗口之前，**写下来**两边各自独占哪些目录、共享哪些文件。§4 每个阶段的表就是这个东西。

**没写下来就双开 = 迟早静默丢代码。**

### 规则 ② 共享文件永远串行

`eko/engine.py`、`config.py`、`runtime/turn.py` 这类被多张卡碰的文件，**同一时刻只能有一个窗口在改**。

判断方法：开卡之前 grep 一下这张卡的"涉及文件"表，和另一个窗口正在做的那张卡对一遍。有交集就等。

### 规则 ③ 用 worktree，不要共用工作目录

```powershell
git worktree add ../RxyCode-lane2 -b feat/lane2
```

两个窗口各自的工作目录和分支，通过 PR 合并。**两个 agent 开同一个目录会互相看到对方写到一半的文件**，产出会莫名其妙。

### 规则 ④ 合并顺序固定：先合小的，后合大的

大卡（P3、L5-3）改动面广，让它最后合并、承担 rebase 成本。反过来会让小卡反复 rebase。

## §6 返工变便宜了，所以两条"先等一等"的建议要改

原来的施工文档里有几处写着"建议等 X 落地再做 Y，否则要返工"。**那是按人的返工成本写的。**

agent 重做一张卡的成本 ≈ 一次执行 + 一次审查，比人重做低一到两个数量级。所以：

| 原建议 | 现在怎么看 |
|---|---|
| "LinkAgent L2 等 RxyCode Phase 2，否则接受一次返工" | **仍然建议等**，但理由变了：不是怕返工，是**怕你审两遍**。如果窗口 2 闲着，提前做 L2 是划算的——契约测试会告诉你 Phase 2 落地后哪里坏了 |
| "L9-4 等 Phase 3" | **必须等**，这条不是返工问题——没有壳就没有可 fork 的东西 |
| "L5 等 L3" | **必须等**，语义约束，做反了效果是负的 |

**判据**：如果"等"的理由是**返工成本**，现在可以重新考虑；如果理由是**没有前置产物**或**做反了结果是错的**，那还得等。

## §7 三个模型怎么配合

[主计划 §11.3](./rxycode/00-EXECUTION-PLAN.md) 定的分工在双开下仍然成立，但有一处要调整：

| 模型 | 职责 | 双开下的变化 |
|---|---|---|
| **Composer 2.5** | 两个窗口都是它，按卡写代码 | — |
| **Grok 4.5** | 查外部资料（provider API、模型定价、各家 vision 格式） | **不占泳道**，需要时临时开 |
| **Sonnet 5** | Diff 审查 | **价值上升了。** 你是瓶颈，让它先过一遍 diff 能省你不少时间 |

**最值得让 Sonnet 5 先审的四张卡**（改动面广、错了不容易发现）：

| 卡 | 为什么 |
|---|---|
| RxyCode **P3**（抽 Session 层） | 全项目最大的一次搬运 |
| RxyCode **B2**（拆全局单例，Phase B） | 漏一个单例就会在多 Agent 下随机出错 |
| LinkAgent **L3-2**（作用域硬门） | 改的是检索语义，错了整个系统效果反向 |
| LinkAgent **L5-3**（AED 蒸馏） | 判断"轨迹算不算成功"，错了会把失败经验入库 |

## §8 一页速查

```
阶段 0   窗口1 RxyCode Phase 0 (8卡)      ‖  窗口2 LinkAgent L0+L1 (11卡)
           │                                    │
阶段 1   窗口1 RxyCode Phase 1 (6卡)      ‖  窗口2 L10-2/1/5 → L8-2/L8-3 或 空
           │   🚪 评测说真话——审查带宽的放大器
阶段 2   窗口1 RxyCode Phase 2 (8卡)      ‖  窗口2 预置包内容 / 可帮 P2
           │   🚪 协议落地——两条线的共同地基
           ├────────────────────────────────────┐
阶段 3   窗口1 Phase 3 Desktop (8卡)      ‖  窗口2 L2→L3→L4→[L10-4]→L5→L6
           │                                 ‖         + L7/L8/L10-3 (30卡)
           │                                    │
           │                              ★ 决策点：L7 首次基线
           │                                    │
阶段 4   窗口1 L9-1/L9-2 → Phase A        ‖  窗口2 L9-3~L9-8 (前端)
                                                │
                                          LinkAgent Desktop
```

| 门 | 开了才能做 |
|---|---|
| RxyCode Phase 1 出口 | 后面每张卡的基线比对 |
| RxyCode Phase 2 出口 | LinkAgent L2、L9-1 |
| RxyCode Phase 3 出口 | LinkAgent L9-4 |
| LinkAgent L3 跨域回归 = 0 | LinkAgent L5、L7、L8-1 |
| LinkAgent L3-3 合并 | LinkAgent L8-4（同一个文件） |
| LinkAgent L5-6 合并 | LinkAgent L10-3（同一个文件） |
| LinkAgent **L10-2** | LinkAgent **L8-2**（不许自己写解析器） |
| ★ L7 首次基线 | LinkAgent L9 整个阶段 |

> ⚠ **L10-4 不是"门"，是"欠债"。** 它不阻塞任何卡，所以很容易被一路推后到最后。但在它合并之前，L3/L4/L5 做出来的治理效果都能被一句 `skill("xxx")` 抵消——**如果你在 L7 首次基线之前还没做它，基线测出来的"治理有效性"是不可信的**。

**推迟到决策点之后再谈的**：RxyCode Phase B（多 Agent）、Phase C（多模型）、Phase D（多模态）。

> 推迟 Phase B 是有依据的，不是随手砍：[`PHASE-B`](./rxycode/PHASE-B-MULTI-AGENT-ORCHESTRATION.md) §2.5 自己引的实测数据是**多 Agent 消耗 15 倍 token，而 Anthropic 明确说编码任务本就不是多 Agent 的强项**。在有更强证据之前，它排在 LinkAgent 后面是合理的。
